# 起動・安定性の再監査（2026-11-09）

## 対象

- GitHubの公開リリース `v0.2.0` ビルド4を通常のダウンロードURLから取得。SHA-256は `5a3c1306298a30c06a084ccf9e7744c8d303e84e71dc0706955a14c34a5f3309`。
- `main` の `af2b8bc` を起点に、起動処理、設定復元、WebKitの生成・終了・通信失敗、Notion API同期、アイコンキャッシュ、インストール処理を確認。
- 検証端末はApple Silicon、Swift 6.3、macOS SDK 26.4。OSの表示は `Version 27.2 (Build 26B123)`。

## 修正した問題

| 問題 | 修正 |
| --- | --- |
| 復元履歴の保存失敗で現在のセッション保存も失敗し、終了を妨げる | 通常の履歴保存は警告して継続。現在状態は独立して保存する。復元前の強制チェックポイントは引き続き必須 |
| 旧 `browser-split.json` の書き込み・削除失敗がセッション保存を失敗扱いにする | Split Viewの状態はセッションJSONへ一括保存。旧ファイルは移行時の読み込みだけに使用 |
| 復元履歴の一覧取得エラーを「履歴なし」とみなして新規状態を作る | 読み取り不能を明示的なエラーとし、元の保存データを保持 |
| 不完全なAPI一覧を0件として受け入れ、ローカルのお気に入りを消す可能性 | 一覧構造とページ送りを検証し、失敗した同期元の既存データを保持 |
| APIのHTML形式504・429がJSON解析エラーに置き換わる | HTTPステータスを保持。HTML本文をエラーへ転載せず、200のHTMLも同期成功とみなさない |
| APIの同時呼び出しが待機後に同じタイミングで送られる | 待機前に通信枠を予約し、時計変更の影響を受けないuptimeで間隔を管理 |
| 不正なRetry-Afterや繰り返すページ送りで待機・取得が不安定になる | 待機時間を有限値に制限し、進まないカーソルを検出して同期を中止 |
| ページが宣言したfaviconを再起動ごとに取り直す | 取得元と画像のハッシュを確認してディスクキャッシュを再利用。7日の有効期限は読み出しで延長しない |
| faviconの保存時、並び替えの比較ごとにファイル属性を参照する | 各ファイルの日付を一度取得してから並び替える |
| `build.sh --install` が稼働中アプリへ直接コピーする | ステージング・署名検証・renameで置き換え。失敗時はロールバックし、旧アプリを退避 |

## 検証の範囲と限界

公開ビルド4では設定・Cookieのない起動を5回実行し、すべてHTTP 200でNotionログイン画面へ到達した。実サービスで報告と同じ504は今回も再現していない。

ローカルfixtureでは、HTTP 503/504、504からの手動再試行、サブリソースだけの失敗、オフライン復帰、ページプロセス終了、設定破損、保存先異常、API異常応答を確認する。タブの切り替え・Split View・切り離しでは未送信の入力と既存WebViewを保持する。自動タブ破棄は追加していない。

Notion／VPN／プロキシが返す504をアプリから完全になくすことはできない。本監査は、アプリがエラーを隠す、設定を失う、無限再試行する等の問題を防ぐためのもの。別macOS、MDM管理端末、Gatekeeperの初回許可、すべてのWebサイトに対する保証ではない。実際のNotionへのページ作成・DB更新は検証で行わない。

## 修正版の検証結果

- WebKit統合テスト297項目が成功（設定破損・保存先異常・API異常・faviconの再利用を含む）。
- 共通処理15件・60アサーションが成功。
- 別の空ディレクトリと新しいSwiftビルドキャッシュ、アドホック署名でクリーンビルド成功。そのアプリでも空の設定から3回起動し、すべてHTTP 200・ログイン画面へ到達。
- NotionのDB準備／同期fixtureが成功。応答消失後の再照合、競合保護、秘密を含まない保存を維持。
- 修正版で設定・Cookieのない起動を10回行い、すべてHTTP 200でログイン画面へ到達。
- 隔離したGUIアプリで初回ガイド3ステップを完了し、ログイン画面のメール欄を確認。
- 200回のタブ切り替え／Split View、20回の切り離し、40回のタブ生成／破棄で既存ページ・未送信入力・エンジン解放を確認。
- インストーラーで初回配置、既存アプリ更新、不正署名の拒否、差し替え後の検証失敗からのロールバックを確認。

診断実行に使ったDMG直下や一時フォルダの起動で、WebKitが `sandbox_extension_issue_file_to_process` をstderrへ出すことがある。今回の該当起動ではHTTP 200・コンテンツ表示に成功しており、このログを504の原因とは判断していない。
