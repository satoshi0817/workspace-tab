# パフォーマンス・安定性調査（2026-11-07）

## 確認した処理

BrowserStoreのエンジン生成・破棄・5秒周期保存、WebKit KVOとCSS反映、表示中ペイン、画像読込、Notion同期・画像取得、Raycast一覧の更新処理を調査した。

## 修正

| 問題 | 対応 |
| --- | --- |
| 変更なしでもセッションをJSON化し、同じファイルを複数回読込 | 保存済み状態との比較で省略。変更時の読込も1回に集約 |
| Split参照を周期ごとに上書き | 変更時だけ書込 |
| Raycastの連携トークン・一覧ファイルの反復読込／権限設定 | トークンと生成済み一覧をメモリ保持。変更時だけ永続化 |
| Raycast一覧を2秒ごとにJSON解析・React再描画 | ファイルのinode・更新日時・サイズが変わった場合だけ読込。重複読込も抑止 |
| 表示のたびにアプリタブ・お気に入り画像を読込 | NSCacheで再利用。最大128px、256件・16MiBを目安に保持（OSが適宜解放） |
| Notionの画像を毎回ダウンロード | ページID・更新日時のファイルが存在すれば再利用。大きな応答は一時ファイルに取得後サイズ検証 |
| 複数のWebKit通知で同じ状態を反復更新 | 同一実行キュー内の更新をまとめる |
| 名前などの編集やページ読込完了で同じCSSを再設定 | スクリプトが変わった場合だけ反映。ナビゲーション時は登録済みUserScriptを利用 |
| 閉じたタブの監視終了が暗黙的 | KVOをinvalidateし、delegate・親Viewを明示的に解除 |
| ペインのエラー表示がEngineを監視していない | エラー表示を独立したObservedObject Viewに分離 |
| Notion同期結果が同じでもUIを再通知 | お気に入りの変更がある場合だけ反映 |
| タイマーの再登録・起床 | 既存Notionタイマーを解除してから登録し、タイマーに許容遅延を設定 |

## 検証

ローカルHTTP fixture・一時WebKitプロファイルの自動テストで確認：

- 変更なしの保存100回：セッション／Raycast一覧の書込0回。
- 同一アイコン1,000回参照：デコード1回、1024pxのテスト画像を最大128pxに縮小。
- WebKit状態更新100回：1回の更新パスに集約。
- タブを閉じた後、weak参照しているBrowserEngineが解放される。
- 全タブ検索で非表示ページのWebViewを生成しない。
- Notionアイコンは、2回目のURLが接続不能でもディスクキャッシュから取得できる。
- 既存のCookie分離、Split、別ウインドウ、保存・復元、ショートカット、Raycast認証、Notion競合処理も検証。

計測例（単発・小規模fixture、全アプリの速度比較ではない）：変更なしの保存＋検索100回 2.89ms、キャッシュ画像参照1,000回 41.73ms。

## 残る制約・切り分け

WKWebViewは初回表示時に作成し、表示済みのタブは閉じるまで保持する。未送信入力、編集中ページ、音声・会議状態を損なわないため、自動で非表示タブを破棄する機能は追加していない。Notion自体のJavaScriptやページ数に依存するWebContentプロセスのメモリは引き続き必要。

更新前の実機ではWebContentプロセス終了の表示があった。該当する診断レポートは見つからず、OSのメモリ圧迫・サイト側・WebKit不具合のどれかは断定できない。メモリ使用量やNotion読込速度の改善率を示す同条件の長時間比較は未実施。プロセス終了が完全に解消したとは主張しない。
